# django-admin-commands

Запуск management-команд Django из админки: с белым списком, аудитом и —
главное — с возможностью остановить то, что уже бежит.

Инструмент решает конкретную проблему: доступ к прод-серверу по SSH есть у
одного человека, поэтому все рутинные операции идут через него. Раздать SSH
нельзя, а раздать *отдельные операции* — можно.

## Что внутри

* **Белый список в коде.** Команда становится запускаемой, только если её
  зарегистрировали в `admin_commands.py`. Конфигурация в БД может лишь
  *выключить* команду, но никогда не добавить новую: иначе любой, у кого есть
  доступ к инструменту, выдал бы себе запуск чего угодно.
* **Форма вместо строки аргументов.** Поля генерируются из `argparse`-парсера
  самой команды: типы, `choices`, обязательность, help. Права защищают от
  злоупотребления, а типизированная форма — от опечатки, то есть от того, как
  прод роняют на самом деле.
* **Команда живёт в отдельном процессе.** Не `call_command()` внутри воркера, а
  настоящий `Popen` в своей process group. Отсюда PID, честные SIGTERM/SIGKILL,
  полный перехват вывода (включая traceback и печать библиотек) и невозможность
  утянуть воркер за собой в OOM.
* **Остановка через БД.** Кнопка «остановить» пишет флаг в строку `Run`, а
  супервизор его вычитывает. Никаких broadcast-RPC: работает одинаково, на
  скольких бы хостах ни крутились воркеры.
* **Таймаут, приоритет, лимиты параллелизма, ключ блокировки.** Ограничения не
  на того, *кто* запускает, а на *сам факт* запуска.
* **Heartbeat и статус `unknown`.** Если супервизор умер, запуск не остаётся
  висеть «выполняется» — но и не объявляется упавшим: инструмент аудита не
  должен врать о том, чего не знает.
* **Журнал неизменяем.** `Run` нельзя отредактировать или удалить через админку.

## Установка

```bash
pip install django-admin-commands
```

```python
INSTALLED_APPS = [
    ...,
    "django.contrib.admin",
    "django_admin_commands",
]
```

```bash
python manage.py migrate
```

Дальше выдайте нужным людям право `django_admin_commands.run_command` — и всё,
интерфейс появится в админке.

## Регистрация команды

`myapp/admin_commands.py`:

```python
from django_admin_commands import CommandSpec, registry

registry.register(
    CommandSpec(
        name="recalculate_stats",
        title="Пересчёт статистики",
        description="Полный пересчёт витрин. Тяжёлая, но безопасная к перезапуску.",
        timeout=3600,
        interruptible=True,  # команда переживает прерывание
        idempotent=True,  # повторный запуск с нуля безвреден
        nice=10,  # не конкурировать с прод-трафиком за CPU
        max_parallel=1,
        lock_key=lambda arguments: arguments.get("tenant"),
    )
)
```

`interruptible` и `idempotent` — это **декларация**, а не настройка поведения.
Инструмент не может сделать небезопасную команду безопасной; он показывает
оператору, чего ожидать, и не даёт запустить то, чего нет в списке. Безопасно
прерываемой команду делает её собственный код: короткие транзакции,
персистентный прогресс, проверка флага отмены в безопасных точках.

## Настройки

Всё в одном словаре:

```python
ADMIN_COMMANDS = {
    "RUNNER": "django_admin_commands.runners.celery.CeleryRunner",
    "DEFAULT_TIMEOUT": 900,
    "MAX_PARALLEL_RUNS": 3,
    "HEARTBEAT_INTERVAL": 5,
    "TERMINATE_GRACE": 20,
    "ARCHIVE_OUTPUT": True,
}
```

Полный список с пояснениями — в `django_admin_commands/conf.py`.

### Раннеры

* `runners.thread.ThreadRunner` (по умолчанию) — супервизор в фоновом потоке
  веб-процесса. Годится для разработки и небольших установок.
* `runners.celery.CeleryRunner` — супервизор в celery-задаче. Для прода.
  Заведите **отдельную очередь** (`CommandSpec.queue`) и отдельный пул
  воркеров: иначе первый же длинный запуск займёт воркеров общей очереди и
  остановит письма, вебхуки и прочую фоновую рутину.

### Обязательный жнец

```
*/1 * * * * python manage.py admin_commands_reap
```

Без него запуски, чей супервизор умер, навсегда останутся в статусе
«выполняется».

## Демо-стенд

```bash
docker compose up --build
```

Админка на http://localhost:8000/admin/, учётки `admin/admin` (полный доступ) и
`operator/operator` (только право запуска). Веб и воркер — разные контейнеры,
так что видно главное: команду исполняет один процесс, кнопку «остановить»
жмут в другом, и всё сходится через БД.

Что стоит попробовать руками:

1. Запустить «Долгую задачу» на 120 секунд и посмотреть живой вывод.
2. Нажать мягкую остановку — команда получит SIGTERM.
3. Запустить её же и убить контейнер воркера (`docker compose kill worker`):
   через полминуты жнец переведёт запуск в `unknown`, а не соврёт про успех.
4. Поставить таймаут в 5 секунд и убедиться, что команду снимут без участия
   человека.
